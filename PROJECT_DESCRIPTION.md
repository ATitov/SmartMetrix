# Описание проекта SmartMetrix

## 1. Назначение

SmartMetrix — программно-аппаратная edge-платформа для автоматической оценки блочности и
трещиноватости карьерного борта. Система получает синхронные изображения с трёх камер,
восстанавливает трёхмерную геометрию поверхности, выделяет блоки и трещины, рассчитывает
гранулометрические характеристики и привязывает результат к локальной системе координат карьера.

Платформа предназначена для работы рядом с измерительным оборудованием, в том числе при
нестабильной или отсутствующей связи с внешней инфраструктурой. Исходные данные и результаты
сначала сохраняются локально, а подтверждённые измерения могут синхронизироваться с облачной
системой после восстановления соединения.

## 2. Основные задачи

SmartMetrix решает следующие задачи:

- проверяет готовность платформы и условия начала измерения;
- синхронно получает кадры с трёх промышленных камер;
- контролирует качество кадров: смаз, пересвет, пыль и недостаточную текстуру;
- строит карты глубины для нескольких стереопар и объединяет их по достоверности;
- выделяет границы блоков и трещин;
- рассчитывает размеры блоков, D10, D20, D50, D80, D90 и дополнительные показатели;
- определяет положение системы на момент экспозиции;
- переносит результаты в локальную систему координат карьера;
- сохраняет исходные данные, промежуточные артефакты и журнал обработки;
- предоставляет операторский и инженерный интерфейсы;
- синхронизирует подтверждённые результаты с внешней системой.

## 3. Измерительная конфигурация

Базовая аппаратная конфигурация включает три синхронизированные камеры A, B и C с объективами
16 мм. Камеры образуют стереопары AB, BC и AC с базисами 0,7 м, 0,8 м и 1,5 м. Короткие базисы
обеспечивают устойчивое восстановление ближних объектов, а длинный базис повышает точность на
больших расстояниях.

Время измерения определяется аппаратной меткой экспозиции. Координаты и ориентация платформы
интерполируются именно на этот момент, чтобы движение оборудования и задержки программной
обработки не искажали пространственную привязку.

## 4. Архитектура

Система построена как набор независимо запускаемых сервисов на .NET 10 и ASP.NET Core.
Крупные изображения и облака точек передаются между этапами через объектное хранилище; в
сообщениях и API используются только URI, метаданные и контрольные суммы.

### Основные сервисы

| Компонент | Ответственность |
|---|---|
| `TriggerService` | Проверка остановки платформы, вибрации и готовности оборудования |
| `MeasurementOrchestrator` | Жизненный цикл измерения, идемпотентные команды, таймауты и повтор обработки |
| `CameraService` | Синхронный захват кадров A/B/C и передача оригиналов в хранилище |
| `QualityService` | Оценка пригодности кадров для последующей обработки |
| `DepthService` | Стереореконструкция, confidence-карты и слияние результатов нескольких базисов |
| `SegmentationService` | Сегментация блоков и трещин с помощью ONNX/TensorRT-бэкенда |
| `BlockAnalysisService` | Расчёт геометрии, распределений размеров и показателей блочности |
| `LocalPositioningService` | Определение позы платформы в локальных координатах |
| `ControlPointService` | Управление опорными точками и импорт геодезических данных |
| `CalibrationService` | Хранение версионированных калибровок камер |
| `GeoreferenceService` | Пространственная привязка результатов к системе координат карьера |
| `StorageService` | Объектное хранение и проверка целостности артефактов |
| `CloudSyncService` | Надёжная отложенная синхронизация подтверждённых результатов |
| `ApiGateway` | API, аутентификация, операторский и инженерный интерфейсы |

### Инфраструктура

- NATS JetStream используется для доменных событий и устойчивой доставки сообщений.
- MinIO используется для кадров, карт глубины, масок, облаков точек и отчётов.
- PostgreSQL/PostGIS предусмотрен для метаданных и пространственных данных.
- OpenTelemetry обеспечивает трассировку, метрики и экспорт телеметрии.
- JSONL-журналы позволяют локально диагностировать каждый сервис без внешней системы логов.

### Native-границы

Аппаратные и GPU-зависимости изолированы от управляемого кода узкими C ABI-адаптерами:

- `CameraService` использует `smartmetrix_arena` для интеграции с Arena SDK;
- `DepthService` использует `smartmetrix_stereo` для OpenCV CUDA/VPI;
- `SegmentationService` использует ONNX Runtime или TensorRT.

Такое разделение позволяет запускать и тестировать основную бизнес-логику без установленных
vendor SDK, а аппаратные реализации собирать отдельно под целевой компьютер.

## 5. Поток обработки измерения

1. `TriggerService` подтверждает допустимые условия запуска.
2. `MeasurementOrchestrator` создаёт измерение в состоянии `Requested`.
3. `CameraService` синхронно захватывает и сохраняет три исходных кадра.
4. `QualityService` проверяет качество каждого кадра.
5. `DepthService` строит и объединяет карты глубины.
6. `SegmentationService` формирует маски блоков и трещин.
7. `BlockAnalysisService` объединяет 2D-сегментацию с 3D-геометрией и рассчитывает показатели.
8. `LocalPositioningService` выдаёт позу на момент экспозиции.
9. `GeoreferenceService` преобразует результат в систему координат карьера.
10. Измерение переходит в `Completed`, после чего может быть передано в облако.

Основной жизненный цикл:

`Requested → Capturing → QualityControl → Reconstructing → Analysing → Georeferencing → Completed`

Ошибочные или отклонённые измерения переходят в `Failed` или `Rejected`. Их можно повторно
запустить с сохранением журнала предыдущих переходов. Команды содержат уникальный идентификатор
и ожидаемую версию состояния, поэтому повторный запрос не создаёт дублирующее измерение.

## 6. Данные и воспроизводимость

Каждое измерение связывает результат с версиями:

- набора входных данных;
- модели сегментации;
- калибровки камер;
- алгоритма обработки;
- преобразования системы координат.

Исходные кадры и применённые версии должны оставаться неизменными. Это позволяет повторить
обработку, сравнить результаты разных версий алгоритма и объяснить происхождение каждого
выходного показателя.

## 7. Режимы работы

### Симуляция

Детерминированные симуляторы позволяют проверять камеры и полный конвейер без реального
оборудования. Эталонный E2E-набор формирует отчёт, облако точек, маску сегментации, confidence-карту
и provenance каждого этапа.

### Локальное развёртывание Windows

Прикладные сервисы, NATS и MinIO могут запускаться как отдельные локальные процессы. Скрипты в
`deploy/local` выполняют публикацию, запуск, остановку, проверку состояния, ротацию журналов и
установку автозапуска.

### Edge-развёртывание

Для промышленного узла предусмотрен контейнерный профиль с systemd, watchdog, healthcheck,
резервным копированием и ограничением объёма локальных данных. Все production-секреты должны
поступать через переменные окружения или внешний secret store.

## 8. Пользовательские интерфейсы

Целевой интерфейс — единое веб-приложение с пятью АРМ: оператора комплекса,
геолога / горного технолога, маркшейдера, инженера комплекса и администратора.
Все пять АРМ включены в проектируемую систему; пользователь может совмещать роли.
Состав экранов, целевые права и требования описаны в [docs/web-gui.md](docs/web-gui.md).
Ниже описаны существующие базовые операторский и инженерный интерфейсы;
они подлежат развитию до целевого состава АРМ.

Операторская панель предназначена для наблюдения за состоянием системы, просмотра измерений и
запуска разрешённых операций. Инженерная панель дополнительно показывает конфигурацию, системные
показатели и журналы, а также предоставляет диагностические команды.

Доступ разделён по ролям оператора, инженера и администратора. Поддерживаются cookie-сессии для
веб-интерфейса и API-ключи для системной интеграции. Опасные операции требуют повышенной роли и
записываются в аудит.

## 9. Надёжность и наблюдаемость

Каждый сервис предоставляет:

- `/health` для проверки жизнеспособности;
- `/ready` для проверки готовности принимать работу;
- `/info` со сведениями о приложении;
- структурированные журналы с `CorrelationId` и `MeasurementId`;
- graceful shutdown и единые HTTP-таймауты;
- трассировку и метрики OpenTelemetry.

Измерительный оркестратор сохраняет состояние и после перезапуска продолжает контроль
незавершённых измерений. Cloud Sync использует локальную устойчивую очередь, контрольные суммы и
контрольные точки загрузки.

## 10. Текущее состояние

На текущей ревизии реализованы сервисная архитектура, контракты, жизненный цикл измерения,
симуляторы, объектное хранение, локальный эксплуатационный профиль, веб-интерфейсы и native-границы
камер и стереореконструкции. Решение собирается без предупреждений, автоматические архитектурные и
интеграционные тесты проходят.

Для полноценного промышленного применения ещё требуется:

- собрать native-модули с реальными Arena SDK и GPU-библиотеками;
- подключить и откалибровать три целевые камеры;
- подготовить и валидировать промышленную модель сегментации;
- заменить оставшиеся файловые MVP-хранилища на PostgreSQL/PostGIS;
- выполнить сквозные испытания на реальном оборудовании;
- провести полевой протокол на расстояниях 12, 20 и 30 метров;
- подтвердить точность D50/D80, координат, длительность обработки и допустимую долю брака.

## 11. Критерий результата проекта

Результатом проекта является автономный edge-комплекс, который для каждого допустимого комплекта
синхронных кадров формирует воспроизводимый и пространственно привязанный отчёт о блочности и
трещиноватости, сохраняет доказательные исходные данные, объясняет происхождение результата и
продолжает работу при временном отсутствии внешней связи.
