# Сквозной измерительный конвейер

## Что выполняется

По умолчанию `MeasurementOrchestrator` вызывает работающие сервисы по HTTP. `POST /measurements`
возвращает созданное измерение; фоновый обработчик последовательно выполняет:

| Этап | Действие и сохраняемый результат |
|---|---|
| calibration | Активная калибровка выбранной установки, её версия, checksum и снимок настроек |
| capture | Реальный вызов CameraService, ссылки и SHA-256 трёх кадров, аппаратные метки |
| pose | Поза LocalPositioningService на аппаратную метку камеры A |
| quality | Оценки качества и причины отбраковки |
| depth | PLY, карта уверенности, организованное облако с соответствием точек пикселям |
| segmentation | Маска, карта уверенности и версия алгоритма сегментации |
| analysis | Геометрия блоков, D10/D50/D80/D95, уверенность и версия анализатора |
| georeference | Облако и блоки в запрошенной системе координат |
| result | Итоговый JSON с результатами анализа, геопривязкой и происхождением данных |

Состояния: `Capturing → QualityControl → Reconstructing → Segmenting → Analysing → Georeferencing → Persisting → Completed`.
Подготовка калибровки и получение позы выполняются в состоянии `Capturing`.
`Completed` выставляется только после сохранения итогового JSON. D20/D90 не подменяются другими
процентилями и остаются пустыми, поскольку текущий анализатор их не вычисляет.

## Идентификаторы, хранение и повторы

- `measurement.id` — логическое измерение; `pipeline.runId` — отдельная попытка обработки.
  В URL обрабатывающих сервисов `measurementId` равен **runId**. Заголовки `X-Measurement-ID`
  и `X-Correlation-ID` содержат логический ID. Итоговый JSON содержит оба ID.
- Все артефакты одной попытки находятся под `measurements/{runId}/` в StorageService;
  ответы этапов — `pipeline/{stage}.json`. Ссылки имеют вид `s3://...` и читаются через
  проверяющий целостность endpoint StorageService, а не как произвольные внешние URL.
- Оркестратор сохраняет версии состояния, ссылки, счётчики попыток и ошибки в
  `data/measurements`. При рестарте он пропускает уже сохранённые этапы. Если ответ этапа
  успел попасть в объектное хранилище, но локальный checkpoint ещё не записан, он восстанавливается оттуда.
- Клиент повторяет запуск с тем же `commandId`. Если `measurementId` не указан, он равен
  `commandId`. Панель сохраняет команду при повторной отправке после сетевой ошибки.
- Команда `retry` начинает новую попытку с новым runId. Прежние ссылки остаются в `previousRuns`;
  неизменяемые объекты предыдущей попытки не перезаписываются.
- CameraService сохраняет квитанцию захвата в `data/capture-receipts`. Повтор запроса возвращает
  те же кадры. Если процесс прервался между началом захвата и сохранением квитанции, возвращается
  `CaptureOutcomeUnknown`: оператор должен запустить новую попытку, автоматического повторного захвата нет.
- HTTP 408/429/5xx и сетевые ошибки повторяются ограниченно (`MaximumAttempts`, по умолчанию 3).
  `NotConfigured` и ошибки входных данных не повторяются. Ошибки попыток доступны в `pipeline.failures`.
- Отмена меняет версию состояния и прерывает текущий HTTP-запрос. Поздний ответ не может
  перевести отменённое измерение в Completed. Вызов уже начавшегося native-вычисления может
  завершиться на стороне сервиса, но последующие этапы оркестратор не запускает.

Этот файловый контур рассчитан на **один экземпляр оркестратора и один CameraService на установку**.
Несколько экземпляров требуют общего хранилища и распределённого механизма владения работой.

## Настройка

В `appsettings.json` оркестратора или переменных окружения задайте:

```text
Pipeline__Enabled=true
Pipeline__RigId=<rigId активной калибровки>
Pipeline__SceneType=default
MeasurementWorkflow__RunDemoPipeline=false
MeasurementWorkflow__SeedDemoData=false
```

Адреса `Pipeline__CalibrationUrl`, `CameraUrl`, `QualityUrl`, `DepthUrl`, `SegmentationUrl`,
`AnalysisUrl`, `PositioningUrl`, `GeoreferenceUrl`, `StorageUrl` по умолчанию соответствуют портам
локального развёртывания. В edge Compose заданы DNS-имена контейнеров; задайте `SMARTMETRIX_RIG_ID`
в deployment environment. Каталоги `/app/data` оркестратора и камеры должны быть постоянными и доступными на запись.

Без RigId или с отключённым обработчиком `/ready` и запуск возвращают 503. Это проверка конфигурации;
она не подтверждает доступность всех зависимостей или качество калибровки. Ошибки зависимостей
отображаются в конкретном измерении.

Перед запуском необходимы:

1. Активная калибровка A/B/C в CalibrationService, одинаковые размеры Mono8-кадров.
2. Версионированный `excavatorToQuarry` через `POST /api/transforms` в LocalPositioningService.
3. Поток позиционных отсчётов через `POST /api/positioning/{excavatorId}/samples` — массив `PositioningSample`.
   Метки должны использовать ту же шкалу времени, что и камеры. Поза запрашивается через
   `GET /api/poses/{excavatorId}?hardwareTimestampNanoseconds=...&exposedAt=...`.
4. Настроенные CameraService, DepthService, SegmentationService и StorageService.

Буфер поз хранит последние 10 000 отсчётов на экскаватор в памяти. Калибровки и преобразования
также пока являются реестрами в памяти: после рестарта соответствующих сервисов их нужно загрузить снова.
Оркестратор сохраняет снимки уже использованных калибровок и поз независимо от этих реестров.

`Pipeline__CalibrationConfidence` и `StaticTransformCovariance` нужно задавать из проверки
калибровки: значения 1 и нулевая матрица по умолчанию подходят только для синтетического стенда.
`exposedAt` сейчас является временем начала вызова захвата на хосте; аппаратная метка используется
для интерполяции позы. Точное соответствие аппаратного времени UTC относится к интеграции оборудования.

## Ограничения изображения и алгоритмов

- Текущий HTTP-конвейер принимает packed Mono8. Для сегментации яркость копируется в три RGB-канала;
  это не восстановление цвета.
- С `rectification.schemaVersion=2` используются AB, AC и BC. Точки BC переводятся
  из камеры B в A и проецируются с учётом дисторсии A; слияние учитывает глубину и confidence.
  Старый формат версии 1 и режим без карт сохраняют AB/AC.
- Если активная калибровка содержит `rectification`, DepthService применяет карты пар,
  восстанавливает точки с intrinsics соответствующей пары и переносит их в исходную
  пиксельную сетку A для сопоставления с маской. См. [подключение карт](pipeline-rectification.md).
  В этом режиме `Pipeline__FramesAreRectified` должен быть false. Без карт старый режим
  требует действительно ректифицированных кадров; иначе — `RectificationNotConfigured`.
  Сам флаг изображения не исправляет.
- Сегментация остаётся детерминированной, поэтому текущие результаты имеют `isTestData=true`,
  даже при аппаратном захвате. Замена её настоящей моделью — отдельный следующий этап проекта.
- Низкая уверенность сегментации сохраняется как диагностический признак; отсутствие валидных
  точек или блоков приводит к Rejected. Некачественные кадры прекращают конвейер до реконструкции.
- Крупные HTTP-запросы и JSON-облака пока ограничены памятью и настройками размера тела сервера.
  На полном разрешении оборудования требуется отдельная проверка производительности.

## Воспроизводимая проверка

```powershell
dotnet build SmartMetrix.sln --no-restore --configuration Release
dotnet test tests/SmartMetrix.ArchitectureTests/SmartMetrix.ArchitectureTests.csproj --no-build --configuration Release --filter FullyQualifiedName~PipelineHttpIntegrationTests
```

Тесты запускают девять отдельных процессов сервисов на свободных loopback-портах и используют
локальный неизменяемый сервер артефактов вместо MinIO. Проверяются расчёт через реальные HTTP API,
повтор команды и квитанции захвата, отбраковка, retry, отмена, временный отказ, HTTP-таймаут,
ограничение повторов и рестарт оркестратора с сохранёнными checkpoint. Это не аппаратные и не MinIO-испытания.

Для ручной проверки в панели:

1. Запустите `tools/initialize-pipeline-simulator.ps1`, чтобы создать три синтетических кадра 128×64.
2. До запуска сервисов задайте `Camera__Adapter=Simulator`, `Camera__SimulatorFrameDirectory` равным
   выведенному абсолютному пути, `Depth__Backend=Cpu`, `Pipeline__RigId=pipeline-simulator-v1` и отключите
   `MeasurementWorkflow__RunDemoPipeline`. Для валидации CameraOptions задайте три разных тестовых серийных номера.
3. Запустите сервисы и выполните `tools/initialize-pipeline-simulator.ps1 -Register`.
4. В панели создайте измерение для `EX-SIM` в системе `quarry:simulator`.

Исходные маленькие fixtures CameraService предназначены только для тестирования захвата;
для сквозного расчёта нужны изображения, созданные этим скриптом. Для отдельной демонстрации интерфейса
можно явно включить `MeasurementWorkflow__RunDemoPipeline=true`: рабочий обработчик тогда не запускается.

Результаты этапов доступны через `GET /measurements/{id}/stages/{stage}` и авторизованный gateway
`GET /api/operator/measurements/{id}/stages/{stage}`. В деталях панели есть кнопки скачивания JSON.
Автозапуск подключается через `CaptureTrigger` и durable consumer NATS: проверяются установка,
экскаватор и срок действия запроса; повтор доставки использует прежние идентификаторы.
Для автоматической отправки завершённых результатов включите `CloudDispatch__Enabled=true`
и задайте `CloudDispatch__BaseUrl`. Отдельный фоновый обработчик передаёт результаты в CloudSync,
не блокируя измерительный цикл. Настройки, повтор после сбоя и состав архива описаны в
[cloud-sync.md](cloud-sync.md).
