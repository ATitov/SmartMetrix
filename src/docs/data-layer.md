# Слой данных SmartMetrix

Сервисы поддерживают PostgreSQL через модуль `SmartMetrix.Persistence`. Измерения, результаты этапов,
справочники, пользователи, аудит, очередь синхронизации и каталог артефактов сохраняются в базе.
HTTP API остаются прежними. MinIO продолжает хранить файлы; файловый режим сохранён для разработки.

## Включение

Для каждого сервиса, работающего с данными, задайте переменные окружения:

```powershell
$env:Persistence__Provider = 'Postgres'
$env:ConnectionStrings__SmartMetrix = 'Host=127.0.0.1;Port=5432;Database=smartmetrix;Username=smartmetrix;Password=<password>'
```

В `deploy/edge/compose.yml` PostgreSQL включён для сервисов по умолчанию; строка подключения поступает
из `edge.env` в `ConnectionStrings__SmartMetrix`. Пример — `deploy/edge/edge.env.example`.
В корневом `docker-compose.yml` к БД подключён StorageService; запускаемые отдельно .NET-сервисы
получают эти переменные из своего окружения. Скрипт локального запуска наследует окружение вызывающего процесса.

Если `Persistence:Provider` не задан, используется прежний режим `File`:
калибровки, опорные точки и преобразования в этом режиме по-прежнему находятся в памяти.
При выборе `Postgres` отсутствие строки подключения или недоступность БД останавливает запуск;
автоматического переключения на файлы нет. Проверка `/ready` включает доступность PostgreSQL.

## Хранилища и границы сервисов

| Схема | Содержимое |
|---|---|
| `measurement` | Текущее состояние измерений, версия, признаки тестовых данных, история снимков, неизменяемые результаты этапов по `run_id` |
| `calibration` | Калибровки, версии, интервалы действия, статусы и аудит |
| `control_point` | Версии опорных точек, наблюдения, использование и аудит |
| `positioning` | Версии преобразований координат; поля Vector3 и Quaternion сохраняются полностью |
| `operator` | Пользователи и хеши паролей, роли и области доступа, решения оператора, аудит, история конфигурации |
| `cloud_sync` | Элементы очереди, контрольные суммы, прогресс отправки, попытки и аудит |
| `camera` | Намерение захвата и завершённые квитанции |
| `storage` | Проверенные метаданные артефактов, постоянный S3 URI, размер, SHA-256 и происхождение |

Схемы разделяют владение данными. Права PostgreSQL следует выдавать отдельным ролям сервисов при
развёртывании; один общий пользователь в примере Compose не обеспечивает изоляцию прав.

Измерения, пользователи, калибровки, версии опорных точек, наблюдения, преобразования,
решения оператора, конфигурационные ревизии, квитанции, артефакты и элементы очереди
хранятся отдельными строками в именованных таблицах. Журналы также разделены на записи.
Идентификаторы и версии имеют ограничения уникальности; использование опорной точки связано
внешним ключом с её версией. Вложенные параметры и существующие контракты сохраняются в JSONB.
Неизменившиеся строки не переписываются. Запись реестра пока использует общий сервисный lock
и загружает его целиком; это ограничивает пропускную способность очень больших реестров.
Выбор следующего элемента очереди и чтение её аудита выполняются SQL-запросами с ограничением.
Сырые пароли и временные presigned URL не сохраняются.

Миграция 005 автоматически переносит прежние документы в таблицы и архивирует исходные
значения в legacy_documents в одной транзакции. Перед обновлением остановите старые версии
сервисов: смешанный запуск старой и новой версии не поддерживается. Повторный запуск безопасен;
обнаружение повторной записи старого формата после переноса останавливает миграцию.

## Транзакции и восстановление

- Обновление измерения выполняется условием `WHERE version = expectedVersion`; версия увеличивается на единицу.
  Запись нового состояния, списка обработанных команд, исторического снимка и события outbox выполняется одной транзакцией.
- Изменения реестра читают актуальное состояние под транзакционной advisory-блокировкой PostgreSQL.
  Блокировка действует между экземплярами сервиса. Ошибка до commit откатывает изменение.
- Результат этапа неизменяем по паре `run_id, stage`. Повтор с тем же содержимым допустим; другое содержимое отклоняется.
  Исторические запуски сохраняются. SQL-представления включают и сохранённые результаты ещё не завершённых измерений;
  для отчётов нужно явно фильтровать статус измерения и выбранный запуск.
- Запись в MinIO и PostgreSQL не является распределённой транзакцией. Сначала сохраняется объект, затем запись БД.
  Потерянный ответ восстанавливается повторным чтением того же объекта и сохранением в БД до продвижения checkpoint.
- Перед аппаратным захватом в БД фиксируется намерение. Если процесс прервался до записи результата,
  повтор возвращает `CaptureOutcomeUnknown`, а не повторяет съёмку. Захват установки сериализуется между экземплярами.
- Очередь и её аудит сохраняются вместе. Worker-блокировка исключает одновременную отправку двумя worker-процессами.
  Файлы spool остаются на диске; экземпляры одного узла должны видеть одинаковый путь spool.
- Каталог MinIO пополняется после upload и при запросе метаданных существующего объекта. Несовпадение с уже
  сохранёнными метаданными считается ошибкой целостности. Массовое сканирование старого bucket не выполняется.

## Миграции и перенос файлов

Встроенные SQL-миграции выполняются до запуска фоновых процессов и инициализации пользователей.
Каждая схема имеет `schema_versions`. Применение миграций защищено общей транзакционной блокировкой.
Роль первого запуска должна иметь право создавать схему и таблицы. Уже применённые SQL-файлы нельзя менять;
новые изменения оформляются следующей миграцией.

Порядок перехода существующего узла:

1. Остановить запись прежними экземплярами сервисов и сохранить резервную копию файлов, spool и MinIO.
2. Создать целевую БД и настроить подключение. Для первичного переноса использовать пустые схемы.
3. Запустить сервисы с `Persistence__Provider=Postgres` и `Persistence__ImportLegacyFiles=true`,
   сохранив прежние content root и настроенные пути файлов.
4. Проверить измерения, аккаунты, решения, аудит и очередь через API. После успешного переноса убрать флаг импорта.
5. Сохранить исходные файлы до проверки резервного восстановления; импорт их не удаляет и не изменяет.

Импортируются `data/measurements/*.json`, пользователи, решения, конфигурация, аудит оператора,
квитанции и незавершённые захваты, очередь синхронизации и её аудит. Используются пути `OperatorApi`,
`Workstations` и `CloudSync` из конфигурации. Импорт отмечается отдельно для каждой схемы;
повтор завершённого импорта ничего не меняет. Конфликт уже существующих данных останавливает перенос.
При частичном сбое импорт можно повторить, оставив исходные файлы неизменными.

Калибровки, опорные точки и преобразования прежней реализации хранились в памяти:
их нужно экспортировать или получить из исходных настроек до остановки и внести через существующие API.
Старые результаты этапов из MinIO загружаются в БД при обращении к ним через конвейер;
полного фонового переноса всех исторических артефактов нет.

## Запросы и PostGIS

`measurement.results` раскрывает показатели крупности и происхождение результата;
`measurement.blocks` — размеры и координаты отдельных блоков;
`measurement.transitions` — переходы состояния;
`operator.reviews` — решения;
`storage.artifacts` — каталог файлов. Отсутствующие показатели не подменяются нулями.

```sql
SELECT r.measurement_id, r.run_id, r.d50_mm, r.d80_mm, r.confidence
FROM measurement.results r
JOIN measurement.measurements m ON m.id = r.measurement_id
WHERE NOT r.is_test_data AND m.status = 'Completed'
  AND r.run_id = (m.payload #>> '{pipeline,runId}')::uuid
ORDER BY m.updated_at DESC;
```

После основных миграций администратор может выполнить `deploy/database/enable-postgis.sql`
на сервере с установленным PostGIS. Он добавляет `measurement.spatial_blocks` с геометрией центра блока.
Локальные координаты имеют SRID 0 и обязательный `coordinate_system_id`: нельзя смешивать разные системы.
Блоки сохраняются в measurement.block_records транзакционным триггером при записи результата.
Скрипт PostGIS добавляет GiST-индекс выражения центра; выборки должны учитывать coordinate_system_id.

## Проверки и ограничения

`PostgresPersistenceTests` проверяет миграции, конкуренцию, историю, неизменяемость этапов,
восстановление реестров, пользователей, импорт, очередь и прерванный захват на настоящем PostgreSQL.
Для тестов создаются отдельные базы со случайными именами, которые удаляются по завершении.

Дополнительные сценарии находятся в PostgresFailureTests.cs (тот же набор Category=Postgres):
отказ записи outbox после изменения измерения; откат прогресса очереди при отказе аудита;
конкурентные изменения без потери записей; отмена ожидания блокировки и отправки события;
SKIP LOCKED между диспетчерами; независимость inbox по имени потребителя;
ошибка переноса старого реестра с повтором после исправления; конфликт файлового импорта;
откат этапа при ошибке проекции блоков; неизменяемость каталога артефактов;
приоритет и сроки очереди; защита использованной версии опорной точки внешним ключом;
фильтрация измерений и проверка версии. Отказы внедряются в настоящую БД ограничениями CHECK,
чтобы проверить откат уже выполненных записей, а не только ошибки до начала транзакции.

PersistenceConfigurationTests работает без PostgreSQL: проверяет безопасные имена схем,
ошибки конфигурации и отсутствие неявного перехода с PostgreSQL на файлы.
Оба набора запускаются командой:

```powershell
dotnet test tests/SmartMetrix.ArchitectureTests --filter 'Category=Postgres|FullyQualifiedName~PersistenceConfigurationTests'
```


```powershell
$env:SMARTMETRIX_TEST_POSTGRES = 'Host=127.0.0.1;Port=5432;Database=postgres;Username=<test-admin>;Password=<password>'
dotnet test tests/SmartMetrix.ArchitectureTests --filter 'Category=Postgres'
```

Тестовому пользователю требуется право создавать базы. В CI с `SMARTMETRIX_RUN_INTEGRATION_TESTS=true`
тесты запускают PostgreSQL 17 с PostGIS через Testcontainers.

## Доставка событий

MeasurementOrchestrator в режиме Postgres записывает компактное событие MeasurementStateChanged
в постоянный outbox для каждой успешно сохранённой версии.
Большие результаты получают через API. Диспетчер использует FOR UPDATE SKIP LOCKED,
подтверждение JetStream, постоянный счётчик попыток и задержку повторов. Недоступность NATS
не отменяет сохранение измерения и не останавливает сервис. Messaging:DispatchEnabled=false
отключает отправку, сохраняя накопление outbox. После восстановления связи доставка продолжается.
Сбой после ACK до commit может повторить событие с тем же event_id: гарантия at-least-once.

PostgresInboxProcessor.ProcessAsync принимает имя потребителя, event_id и обработчик с
NpgsqlConnection/NpgsqlTransaction. Изменения обработчика и маркер inbox коммитятся вместе;
ошибка откатывает оба. Подтверждайте NATS только после успешного возврата этого метода, включая
возврат false для дубля. Внешние действия нельзя включить в транзакцию БД: отправляйте их через
outbox. Существующий HTTP-конвейер не заменяется подписчиком NATS.

TriggerService не подключается к PostgreSQL и не использует outbox ни в одном режиме.
Он публикует CaptureRequested непосредственно в JetStream и возвращает HTTP 202 только после
подтверждения сохранения. Повторы внутри одного запроса сохраняют event_id, payload и expiresAt;
подтверждение дедупликации JetStream также считается успехом. Без подтверждения возвращается
HTTP 503 CapturePublicationUnconfirmed с eventId, measurementId, expiresAt и deliveryUncertain=true:
событие могло сохраниться, поэтому клиент не должен автоматически создавать новый запрос съёмки.
Cooldown сохраняется и при неопределённом результате отправки.

Trigger:RequestLifetimeMilliseconds задаёт срок действия (по умолчанию 2000 мс),
Trigger:PublishAttempts — число попыток (3), Trigger:PublishTimeoutMilliseconds — ожидание одной
попытки (500 мс). После истечения срока фонового повтора нет. HTTP-запрос после перезапуска
сервиса не имеет постоянной идемпотентности; повтор уже принятой команды нельзя считать новой
оценкой условий без решения вызывающей стороны. Отклонённые условия ничего не публикуют.

CaptureRequested содержит expiresAt. IdempotentEventProcessor проверяет его до и после
получения inbox-блокировки; просроченные события и старые сообщения без срока действия не
вызывают обработчик. Будущий NATS-подписчик должен использовать эту проверку, подтверждать
отброшенные события и передавать исходный measurementId в CaptureReceiptStore для защиты
аппаратной операции при повторной доставке/перезапуске. Часы издателя и потребителя должны
быть синхронизированы. Сейчас рабочего подписчика CaptureRequested в сервисах нет:
аппаратный захват запускается существующим HTTP-конвейером.

После обновления прежняя схема trigger и её записи автоматически не удаляются и не
переотправляются: отложенные команды съёмки могли устареть. Их удаление — отдельная операция
после проверки резервной копии. В edge Compose TriggerService зависит только от NATS.

Интеграция прямой публикации проверяется в TriggerJetStreamTests на изолированном NATS Server
через SMARTMETRIX_TEST_NATS или через Testcontainers в CI.


## Хранение файлов и резервное копирование

В режиме PostgreSQL правило MinIO artifact-retention отключено: файлы результатов сохраняются
без автоматического удаления по возрасту. Очистка незавершённых загрузок .uploads остаётся.
RetentionDays действует только в прежнем режиме File. Удалять файлы опубликованных результатов
независимо от БД нельзя; автоматическое удаление измерений не входит в существующий API.
Контролируйте свободное место и переносите старые данные согласованными резервными копиями.

Из корня репозитория на edge-хосте:

```bash
sudo bash deploy/edge/scripts/backup.sh /mnt/backups/smartmetrix
# При восстановлении все сервисы этого compose-проекта должны быть остановлены.
# Каталог назначения должен отсутствовать; конфигурация и секреты предоставляются отдельно.
sudo bash deploy/edge/scripts/restore.sh /mnt/backups/smartmetrix/<timestamp> /var/lib/smartmetrix-restored
```

backup.sh запоминает запущенные сервисы, останавливает все кроме PostgreSQL, делает pg_dump
и архив всего data root кроме физического каталога PostgreSQL. Копия включает MinIO, NATS,
spool, файлы API и ключи Data Protection. Внешние процессы не должны писать в эту БД/каталог.
EXIT-trap возобновляет ранее запущенные сервисы при успехе и ошибке. COMPLETE появляется только
после создания контрольных сумм. Назначение резервной копии должно находиться вне data root.
Копия содержит чувствительные данные; каталог создаётся с правами 0700.

restore.sh проверяет COMPLETE и SHA-256, разворачивает файлы только в новый каталог и выполняет
pg_restore одной транзакцией. Используйте сохранённую версию приложения из version.env,
те же секреты edge.env и сохраните SMARTMETRIX_DATA_ROOT с новым путём перед запуском сервисов.
Скрипт не запускает прикладные сервисы автоматически: сначала проверьте восстановленные данные.
Проверяйте восстановление на отдельном стенде перед обновлением рабочего узла.
Переключение обратно на File не экспортирует новые записи PostgreSQL.

Реализовано хранение существующих сервисных моделей; справочники новых бизнес-сущностей
потребуют соответствующих доменных API. Позиционирование сохраняется в результате этапа pose,
а не как архив каждого входящего аппаратного отсчёта.
