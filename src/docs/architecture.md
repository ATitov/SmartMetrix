# Архитектура SmartMetrix

## Поток измерения

1. `TriggerService` подтверждает остановку платформы, допустимую вибрацию и готовность камер.
2. `MeasurementOrchestrator` создаёт измерение и запрашивает синхронный захват.
3. `CameraService` получает кадры A/B/C и сохраняет оригиналы через `StorageService`.
4. `QualityService` отбрасывает смаз, пересвет, пыль и недостаточную текстуру.
5. `DepthService` строит глубину для пар AB, BC и AC и объединяет карты по достоверности.
6. `SegmentationService` выделяет границы блоков и трещин.
7. `BlockAnalysisService` объединяет маски и 3D, рассчитывает размеры и распределение.
8. `LocalPositioningService` выдаёт позу на момент экспозиции в локальных координатах.
9. `GeoreferenceService` переносит блоки в систему карьера.
10. `CloudSyncService` реплицирует подтверждённые результаты при наличии связи.

## Правила границ

### Жизненный цикл измерения

`MeasurementOrchestrator` хранит состояние и журнал переходов в PostgreSQL при
`Persistence:Provider=Postgres` или в `data/measurements` в файловом режиме и при старте
возобновляет контроль незавершённых измерений. Команды содержат уникальный `commandId` и ожидаемую
`expectedVersion`: повтор команды возвращает текущий результат без нового перехода, а конкурирующее
изменение отклоняется. Длительность этапа задаётся через
`MeasurementWorkflow__StageTimeoutSeconds`; просроченный этап детерминированно переходит в `Failed`
с причиной в журнале и после этого может быть запущен повторно.

Хранилища остальных сервисов, миграции и порядок перехода с файлов описаны в
[data-layer.md](data-layer.md). В edge Compose включён PostgreSQL; режим локальной разработки
по умолчанию остаётся файловым.

Допустимый основной путь: `Requested` → `Capturing` → `QualityControl` → `Reconstructing` →
`Segmenting` → `Analysing` → `Georeferencing` → `Persisting` → `Completed`. Активный процесс можно компенсировать переходом в
`Rejected` или `Failed`; из этих двух состояний разрешён retry в `Requested`.

Реализованный HTTP-конвейер ручного запуска, checkpoint, артефакты и текущие ограничения
описаны в [measurement-pipeline.md](measurement-pipeline.md). Автоматический запуск подключён через
durable consumer CaptureRequested с проверкой установки и срока действия запроса.
Завершённые результаты передаются отдельным обработчиком в CloudSync при включённом CloudDispatch;
недоступность очереди не отменяет локально завершённое измерение. Аппаратная приёмка реконструкции
и синхронизации проводится отдельно от программных тестов.

- Команды в реальном времени идут по HTTP/gRPC; доменные события — через NATS JetStream.
- Полные изображения и облака точек не передаются в сообщениях: только URI и контрольные суммы.
- Каждый сервис владеет своими данными. Общая БД допустима в MVP только с отдельной схемой на сервис.
- Время экспозиции берётся из аппаратной метки; поза интерполируется именно на него.
- GNSS — лишь один из входов позиционирования. Наружу всегда выдаются локальные XYZ.
- Переходы состояния измерения идемпотентны; повтор события не создаёт повторный результат.

## Native-границы

- `CameraService` → `libsmartmetrix_arena` → Arena SDK.
- `DepthService` → `libsmartmetrix_stereo` → OpenCV CUDA/VPI.
- `SegmentationService` → StoneVision по HTTP для YOLO + MobileSAM;
  [настройка и ограничения](stonevision.md). Backend `Deterministic` служит для тестов;
  native TensorRT/ONNX Runtime остаётся отдельной будущей интеграцией.

До появления аппаратных SDK реализации должны явно возвращать `NotConfigured`, а не генерировать правдоподобные фиктивные измерения.
