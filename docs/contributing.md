# Правила разработки

## Ветвление

`main` — единственная долговременная ветка и всегда должна оставаться пригодной к
сборке. Рабочие ветки создаются от актуальной `main`; рекомендуемые префиксы:
`feature/`, `fix/`, `docs/` и `chore/`. Изменения попадают в `main` только через
pull request. После merge рабочая ветка удаляется.

## Pull request

Каждый pull request должен:

- решать один связный тикет и ссылаться на него через `Closes #...`;
- быть достаточно небольшим для содержательного ревью;
- обновлять тесты и документацию вместе с кодом;
- пройти CI без предупреждений, ошибок и изменений форматирования;
- получить одобрение владельца кода из `CODEOWNERS`;
- не содержать merge-коммитов из `main`; перед merge ветка обновляется rebase.

Для `main` в GitHub следует включить branch protection: запретить прямые push,
требовать pull request с одним одобрением и review от Code Owner, требовать
актуальную ветку и успешную проверку `Restore, format, build and test`, запретить
обход правил и force push. Неуспешная обязательная проверка должна блокировать
merge.

## Локальная проверка

Команды локальной проверки приведены в корневом `README.md`. CI использует тот же
порядок: locked restore, проверка форматирования, Release-сборка и тесты, включая
`SmartMetrix.ArchitectureTests`.
