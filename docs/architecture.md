# Архитектура SmartMetrix

## Поток измерения

1. `TriggerService` подтверждает остановку платформы, допустимую вибрацию и готовность камер.
2. `MeasurementOrchestrator` создаёт измерение и запрашивает синхронный захват.
3. `CameraService` получает кадры A/B/C и сохраняет оригиналы через `StorageService`.
4. `QualityService` отбрасывает смаз, пересвет, пыль и недостаточную текстуру.
5. `DepthService` строит глубину для пар AB, BC и AC и объединяет карты по достоверности.
6. `SegmentationService` выделяет границы блоков и трещин.
7. `BlockAnalysisService` объединяет маски и 3D, рассчитывает размеры и распределение.
8. `LocalPositioningService` выдаёт позу на момент экспозиции в локальных координатах.
9. `GeoreferenceService` переносит блоки в систему карьера.
10. `CloudSyncService` реплицирует подтверждённые результаты при наличии связи.

## Правила границ

- Команды в реальном времени идут по HTTP/gRPC; доменные события — через NATS JetStream.
- Полные изображения и облака точек не передаются в сообщениях: только URI и контрольные суммы.
- Каждый сервис владеет своими данными. Общая БД допустима в MVP только с отдельной схемой на сервис.
- Время экспозиции берётся из аппаратной метки; поза интерполируется именно на него.
- GNSS — лишь один из входов позиционирования. Наружу всегда выдаются локальные XYZ.
- Переходы состояния измерения идемпотентны; повтор события не создаёт повторный результат.

## Native-границы

- `CameraService` → `libsmartmetrix_arena` → Arena SDK.
- `DepthService` → `libsmartmetrix_stereo` → OpenCV CUDA/VPI.
- `SegmentationService` → TensorRT/ONNX Runtime.

До появления аппаратных SDK реализации должны явно возвращать `NotConfigured`, а не генерировать правдоподобные фиктивные измерения.
